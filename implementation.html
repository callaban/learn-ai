Practical Engineering

AI Implementation with PyTorch

From tensors to production: the engineering behind building, training, fine-tuning, and deploying neural networks using PyTorch — the dominant framework for AI research and production.

Why PyTorch

PyTorch was released by Meta AI in 2016 and has become the framework of choice for AI research and increasingly for production. Its core design principle is define-by-run (dynamic computation graphs): the graph is built at runtime as Python code executes, making debugging with standard Python tools natural. TensorFlow 1.x required a separate graph-construction phase; PyTorch eliminated this friction.

Research Dominance

By 2023, over 80% of papers at top ML conferences (NeurIPS, ICML, ICLR) used PyTorch. Nearly every foundational model — GPT, LLaMA, Mistral, Stable Diffusion, Whisper — was first implemented in PyTorch. If a paper publishes code, it is almost certainly PyTorch.

Production Adoption

torch.compile() closes the gap between research and production by compiling dynamic graphs into optimised static representations. Companies running PyTorch in production include Meta, OpenAI, Mistral, Stability AI, and many others.

Tensors: The Core Data Structure

A tensor is an n-dimensional array, generalising scalars (rank 0), vectors (rank 1), matrices (rank 2), and higher-dimensional structures. PyTorch tensors are similar to NumPy arrays but can live on GPU memory and participate in automatic differentiation.

import torch

# Create tensors
x = torch.tensor([[1.0, 2.0], [3.0, 4.0]])  # shape (2, 2)
y = torch.zeros(3, 4)                         # shape (3, 4), all zeros
z = torch.randn(8, 512)                       # shape (8, 512), N(0,1) samples

# Move to GPU
device = "cuda" if torch.cuda.is_available() else "cpu"
x = x.to(device)

# Basic operations — all differentiable
a = x @ x.T                          # matrix multiply, shape (2, 2)
b = torch.softmax(x, dim=-1)
c = x.mean(dim=1, keepdim=True)      # shape (2, 1)

# Shape inspection
print(x.shape)   # torch.Size([2, 2])
print(x.dtype)   # torch.float32
print(x.device)  # device(type='cuda', index=0)
Contiguous Memory and Strides Tensors are stored as a flat buffer with a shape and stride. A stride tells PyTorch how many elements to skip in memory to move one position along each dimension. Operations like .T (transpose) don't copy data — they return a view with swapped strides. Calling .contiguous() forces a physical copy into C-contiguous order, which many CUDA kernels require for peak performance.

Autograd: Automatic Differentiation

PyTorch's autograd engine implements reverse-mode automatic differentiation. Every tensor operation records itself into a computation graph (a directed acyclic graph of Function objects). Calling .backward() on a scalar loss traverses the graph in reverse, computing gradients via the chain rule.

x = torch.tensor([[2.0, 3.0]], requires_grad=True)  # (1, 2)
W = torch.tensor([[1.0, 0.0], [0.0, 2.0]], requires_grad=True)  # (2, 2)
b = torch.tensor([0.5, -0.5], requires_grad=True)   # (2,)

z    = x @ W + b          # linear layer: shape (1, 2)
a    = torch.relu(z)      # activation
loss = a.sum()            # scalar

loss.backward()           # populates .grad for all leaf tensors

print(x.grad)             # ∂loss/∂x
print(W.grad)             # ∂loss/∂W
print(b.grad)             # ∂loss/∂b

No-Grad Contexts

During inference, gradient tracking wastes memory and compute. Wrap inference code in torch.no_grad() to disable the autograd engine:

model.eval()
with torch.no_grad():
    logits = model(input_ids)
    probs  = torch.softmax(logits, dim=-1)

For fine-tuning, selectively freeze parameters by setting requires_grad = False on layers you don't want to update — for example, all layers except the final classification head.

Building Models with nn.Module

All neural networks in PyTorch inherit from torch.nn.Module. A Module encapsulates parameters, child modules, and a forward() method that defines the computation. Modules compose: a Module can contain other Modules, and PyTorch automatically discovers all nested parameters for the optimizer.

import torch
import torch.nn as nn

class FeedForward(nn.Module):
    def __init__(self, d_model: int, d_ff: int, dropout: float = 0.1):
        super().__init__()
        self.linear1 = nn.Linear(d_model, d_ff)
        self.linear2 = nn.Linear(d_ff, d_model)
        self.dropout = nn.Dropout(dropout)
        self.act     = nn.GELU()

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        return self.linear2(self.dropout(self.act(self.linear1(x))))


class TransformerBlock(nn.Module):
    def __init__(self, d_model: int, n_heads: int, d_ff: int):
        super().__init__()
        self.attn  = nn.MultiheadAttention(d_model, n_heads, batch_first=True)
        self.ff    = FeedForward(d_model, d_ff)
        self.norm1 = nn.LayerNorm(d_model)
        self.norm2 = nn.LayerNorm(d_model)

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        # Pre-norm transformer (used by GPT-2+, LLaMA)
        attn_out, _ = self.attn(x, x, x)
        x = self.norm1(x + attn_out)    # residual connection
        x = self.norm2(x + self.ff(x))
        return x


model   = TransformerBlock(d_model=512, n_heads=8, d_ff=2048)
n_params = sum(p.numel() for p in model.parameters())
print(f"Parameters: {n_params:,}")   # Parameters: 3,152,384

The Training Loop

A complete PyTorch training loop has five components: the dataset (raw data), the DataLoader (batching/shuffling), the model, the loss function, and the optimizer. Each training step follows the same four-step pattern:

  1. Forward pass — run the model to get predictions
  2. Compute loss — measure prediction error
  3. Backward pass — loss.backward() computes ∂loss/∂W for all W
  4. Optimizer step — optimizer.step() updates weights; optimizer.zero_grad() clears stale gradients
import torch
import torch.nn as nn
from torch.utils.data import DataLoader, TensorDataset

# --- Synthetic dataset ---
X = torch.randn(1000, 128)
y = (X[:, 0] > 0).long()

dataset = TensorDataset(X, y)
loader  = DataLoader(dataset, batch_size=64, shuffle=True, num_workers=4)

# --- Model and optimizer ---
model     = nn.Sequential(nn.Linear(128, 256), nn.ReLU(), nn.Linear(256, 2))
optimizer = torch.optim.AdamW(model.parameters(), lr=3e-4, weight_decay=0.01)
criterion = nn.CrossEntropyLoss()

# --- Training loop ---
model.train()
for epoch in range(10):
    total_loss = 0.0
    for batch_X, batch_y in loader:
        logits = model(batch_X)                # forward pass
        loss   = criterion(logits, batch_y)    # compute loss

        optimizer.zero_grad()                  # clear stale gradients
        loss.backward()                        # compute gradients
        torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
        optimizer.step()                       # update weights

        total_loss += loss.item()
    print(f"Epoch {epoch+1}  loss={total_loss/len(loader):.4f}")
Common Mistake: Forgetting zero_grad() PyTorch accumulates gradients by default — calling loss.backward() without first calling optimizer.zero_grad() adds to existing gradients. This causes incorrect, diverging updates. Always zero gradients before the backward pass, not after.

Gradient Clipping

clip_grad_norm_ caps the global gradient norm to max_norm before the optimizer step, preventing the exploding gradient problem that can destabilise training on long sequences. The norm is computed across all parameters:

‖g‖₂ = √(Σᵢ gᵢ²) If ‖g‖₂ > max_norm: g ← g · (max_norm / ‖g‖₂)

Learning Rate Schedulers

from torch.optim.lr_scheduler import CosineAnnealingLR, LinearLR, SequentialLR

# Linear warmup for 100 steps then cosine decay to 5% of base LR
warmup    = LinearLR(optimizer, start_factor=0.01, total_iters=100)
cosine    = CosineAnnealingLR(optimizer, T_max=900, eta_min=1.5e-5)
scheduler = SequentialLR(optimizer, schedulers=[warmup, cosine], milestones=[100])

# Call after each optimizer step:
scheduler.step()

Cosine annealing with linear warmup is the de-facto schedule for large-scale pretraining. Warmup prevents large early gradient updates when the optimizer's momentum estimates are unreliable.

Mixed Precision Training

Training in BF16 halves memory use and doubles throughput on Ampere/Hopper GPUs versus FP32, because tensor cores run at 2× the FLOP rate for 16-bit operations. PyTorch's torch.amp module handles this automatically — the forward and backward passes run in BF16, while the master weights and optimizer state stay in FP32.

from torch.amp import autocast, GradScaler

scaler = GradScaler()    # needed for FP16; BF16 does not require loss scaling

for batch_X, batch_y in loader:
    optimizer.zero_grad()

    with autocast(device_type="cuda", dtype=torch.bfloat16):
        logits = model(batch_X)
        loss   = criterion(logits, batch_y)

    scaler.scale(loss).backward()
    scaler.unscale_(optimizer)
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    scaler.step(optimizer)
    scaler.update()
BF16 vs FP16 BF16 and FP32 share the same 8-bit exponent, so BF16 can represent the same dynamic range as FP32. FP16 has only a 5-bit exponent — large activations or gradients can overflow. This is why large-scale LLM training switched from FP16 (GPT-3 era) to BF16 (LLaMA, GPT-4 era): BF16 eliminates loss scaling and is more numerically stable.

Fine-Tuning Pretrained Models

Training a large model from scratch requires millions of GPU-hours. For most applications, the practical path is to fine-tune a pretrained model on task-specific data. The Hugging Face transformers library provides pretrained models and tokenizers for thousands of architectures.

Full Fine-Tuning

from transformers import AutoModelForCausalLM, AutoTokenizer

model_id  = "meta-llama/Llama-3.2-1B"
tokenizer = AutoTokenizer.from_pretrained(model_id)
model     = AutoModelForCausalLM.from_pretrained(
    model_id, torch_dtype=torch.bfloat16, device_map="auto"
)

# All parameters trainable by default
optimizer = torch.optim.AdamW(model.parameters(), lr=2e-5)
# ... standard training loop ...

LoRA: Low-Rank Adaptation

Fine-tuning all weights of a 7B model requires ~14 GB for weights plus ~56 GB for FP32 optimizer state — impractical on most hardware. LoRA (Hu et al., 2021) freezes the original weights and injects low-rank trainable update matrices into attention projection layers.

Original weight: W ∈ ℝᵈˣᵏ (frozen during fine-tuning) LoRA update: ΔW = BA where B ∈ ℝᵈˣʳ, A ∈ ℝʳˣᵏ, r ≪ min(d,k) Modified forward: h = Wx + BAx · (α/r) Trainable parameters: r(d+k) vs d·k for full fine-tuning At rank r=8, d=k=4096: 65,536 vs 16,777,216 — a 256× reduction
from peft import get_peft_model, LoraConfig, TaskType

lora_config = LoraConfig(
    task_type=TaskType.CAUSAL_LM,
    r=8,                                   # rank — higher r = more capacity
    lora_alpha=32,                         # scaling factor α
    target_modules=["q_proj", "v_proj"],   # which weight matrices to adapt
    lora_dropout=0.05,
)

model = get_peft_model(model, lora_config)
model.print_trainable_parameters()
# trainable params: 2,097,152 || all params: 1,235,814,400 || trainable%: 0.17
QLoRA QLoRA (Dettmers et al., 2023) combines 4-bit NF4 quantisation of the frozen base model with LoRA adapters in BF16. A 65B model normally requires ~130 GB; QLoRA reduces this to ~35 GB — fitting on a single A100-80GB. The NF4 data type is optimised for normally-distributed weight values, minimising quantisation error versus INT4.

Datasets and DataLoaders

The torch.utils.data module provides the contract for streaming training data efficiently. A Dataset implements __len__ and __getitem__. A DataLoader wraps it with batching, shuffling, and multi-process prefetching.

from torch.utils.data import Dataset, DataLoader
from pathlib import Path
import json, torch

class TextDataset(Dataset):
    def __init__(self, path: str, tokenizer, max_len: int = 512):
        self.tokenizer = tokenizer
        self.max_len   = max_len
        self.records   = [json.loads(l) for l in Path(path).read_text().splitlines()]

    def __len__(self) -> int:
        return len(self.records)

    def __getitem__(self, idx: int) -> dict:
        text = self.records[idx]["text"]
        enc  = self.tokenizer(text, max_length=self.max_len,
                               truncation=True, padding="max_length",
                               return_tensors="pt")
        return {k: v.squeeze(0) for k, v in enc.items()}


loader = DataLoader(
    TextDataset("data/train.jsonl", tokenizer),
    batch_size=8,
    shuffle=True,
    num_workers=4,        # parallel preprocessing on CPU
    pin_memory=True,      # faster CPU→GPU transfer via pinned memory
    prefetch_factor=2,    # prefetch 2 batches per worker
)
DataLoader Bottlenecks A GPU training a 7B model can consume data faster than a single CPU core can tokenize and batch it. Use num_workers ≥ 4 to parallelize preprocessing. Set pin_memory=True to allocate CPU tensors in pinned (non-pageable) memory, enabling faster DMA transfers to GPU. For very large datasets, the Hugging Face datasets library supports memory-mapped Arrow files that avoid loading all data into RAM.

Production Deployment

Research code uses Python's dynamism freely. Production code must be fast, portable, and able to run without the full Python runtime. PyTorch offers several compilation paths.

torch.compile (PyTorch 2.0+)

The simplest path to faster inference. Wrapping a model with torch.compile() triggers Dynamo (a Python bytecode interpreter) to capture the computation graph and hand it to Inductor (the default backend), which generates optimised Triton or C++/CUDA kernels.

model = torch.compile(model, mode="reduce-overhead")
# Options: "default", "reduce-overhead" (stable shapes), "max-autotune"

# First call triggers JIT compilation (slow); subsequent calls use compiled kernel
with torch.no_grad():
    out = model(input_ids)   # typically 1.5–3× speedup over eager mode

ONNX Export

ONNX (Open Neural Network Exchange) is a portable IR for models. Export once, run anywhere — ONNX Runtime, TensorRT, CoreML, OpenVINO. Essential for deploying to mobile, edge, or non-NVIDIA hardware.

dummy = torch.zeros(1, 128, dtype=torch.long)
torch.onnx.export(
    model, dummy, "model.onnx",
    input_names=["input_ids"],
    output_names=["logits"],
    dynamic_axes={"input_ids": {0: "batch", 1: "seq_len"}},
    opset_version=17,
)

import onnxruntime as ort
sess   = ort.InferenceSession("model.onnx", providers=["CUDAExecutionProvider"])
logits = sess.run(None, {"input_ids": dummy.numpy()})[0]

TorchServe

TorchServe is PyTorch's model serving framework. It handles REST/gRPC endpoints, batching, multiple model versions, and metrics out of the box.

# Package model artifact
torch-model-archiver --model-name mymodel --version 1.0 \
  --model-file model.py --serialized-file model.pt \
  --handler text_classifier

# Start server
torchserve --start --model-store ./model_store --models mymodel=mymodel.mar
# Endpoint: http://localhost:8080/predictions/mymodel

The PyTorch Ecosystem

PyTorch's value extends well beyond the core library. A rich ecosystem of libraries handles data, training orchestration, model hubs, and production serving.

Hugging Face Transformers

The de-facto hub for pretrained models. Provides tokenizers, model architectures, the Trainer API, and the datasets library for thousands of public models. Almost every open-source LLM is available here in PyTorch format.

PyTorch Lightning

Abstracts boilerplate (device placement, gradient clipping, mixed precision, distributed training) into a LightningModule. Useful for research experiments that need to scale to multi-GPU without rewriting the training loop.

torchvision / torchaudio

Domain-specific datasets, transforms, and pretrained models for computer vision (ResNet, ViT, CLIP) and audio (wav2vec, Whisper wrappers). Maintained by the PyTorch core team.

vLLM

High-throughput inference server built on PyTorch with PagedAttention and continuous batching. Standard choice for self-hosted LLM inference. Up to 24× higher throughput than naive implementations on the same hardware.

bitsandbytes

Library for 8-bit/4-bit quantization and optimizers. Powers QLoRA. Its AdamW8bit optimizer cuts optimizer state memory by 4× with near-identical convergence to FP32 Adam.

Triton (OpenAI)

Python-embedded DSL for writing GPU kernels. FlashAttention, many quantization kernels, and torch.compile's Inductor backend all use Triton. Lets researchers write custom, hardware-efficient CUDA kernels without raw CUDA C.

Distributed Training with PyTorch

Single-GPU training is insufficient for models beyond a few billion parameters. PyTorch provides several distributed strategies through torch.distributed.

Data Parallel (DDP)

DistributedDataParallel replicates the full model on each GPU. Each GPU processes a different micro-batch; gradients are all-reduced (summed and averaged) across GPUs at the end of the backward pass. Scales efficiently to ~8–16 GPUs; communication overhead grows at higher GPU counts.

import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP

dist.init_process_group("nccl")   # NCCL backend for GPU-to-GPU comms
model = DDP(model.to(local_rank), device_ids=[local_rank])

# Launch with: torchrun --nproc_per_node=8 train.py

Model Parallel and Pipeline Parallel

When a model doesn't fit on a single GPU, its layers are split across devices. Pipeline parallelism splits the model into stages — GPU 0 runs layers 0–11, GPU 1 runs layers 12–23, etc. — and uses micro-batches to keep all stages active simultaneously. PyTorch's torch.distributed.pipelining module automates this.

3D Parallelism Large-scale training (GPT-4, LLaMA 3 405B) combines three strategies simultaneously: Data Parallelism (replicate across nodes), Tensor Parallelism (split individual weight matrices across GPUs within a node, using Megatron-LM column/row splits), and Pipeline Parallelism (split layers across nodes). This 3D decomposition is the state of the art for frontier model training and is covered in depth on the Training Data Centers page.

FSDP: Fully Sharded Data Parallel

FSDP (PyTorch 1.12+) shards model parameters, gradients, and optimizer state across all GPUs, rather than replicating them. Each GPU holds only 1/N of each tensor. During forward and backward passes, FSDP all-gathers the full parameter shard just in time for each layer, then immediately discards it. This enables training models far larger than a single GPU's memory while approaching DDP throughput.

from torch.distributed.fsdp import FullyShardedDataParallel as FSDP
from torch.distributed.fsdp.wrap import transformer_auto_wrap_policy

model = FSDP(
    model,
    auto_wrap_policy=transformer_auto_wrap_policy,
    mixed_precision=MixedPrecision(param_dtype=torch.bfloat16),
)
