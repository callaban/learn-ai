Data Centers for Consumer AI Inference

Serving a frontier LLM to millions of concurrent users is a fundamentally different engineering problem from training it. Inference data centers are optimised for throughput, cost per token, and strict latency SLOs — not for massive parallel compute.

Training vs Inference: Two Different Worlds

The Serving Architecture

A production LLM serving system has multiple layers between the user and the GPU:

Tensor Parallelism for Serving

A 70B-parameter model at INT4 quantisation requires 35 GB just for weights. An H100 has 80 GB HBM — it fits. But at BF16, 70B requires 140 GB — needs 2 GPUs minimum. At FP32, 280 GB — needs 4+ GPUs. More importantly, a single H100 running decode for a batch of 1 at 70B is memory-bandwidth-limited at a low token rate.

Tensor parallelism shards model weights across multiple GPUs within a serving pod. Each GPU holds a fraction of each weight matrix; they collaborate on every forward pass via all-reduce:

Tensor parallel degree TP: Each GPU holds 1/TP of each weight matrix. Each forward step requires 2 all-reduce calls per layer. All-reduce cost: 2 × hidden_dim / TP bytes per GPU × (TP−1)/TP With NVLink (900 GB/s): all-reduce of 8GB over TP=8 GPUs takes ~8 ms Throughput vs latency tradeoff: TP=1 (1 GPU): low throughput (memory-bandwidth bound), low cost/request TP=8 (8 GPU): 8× weight-read bandwidth → 8× faster decode → 8× tokens/sec but 8× hardware cost per request at same batch size Sweet spot for 70B: TP=4 or TP=8 depending on latency SLO and cost target.

Continuous Batching and PagedAttention

The Problem with Static Batching

Naive inference servers process a fixed batch of N requests together, wait for all N to complete, then accept the next batch. This "static batching" wastes GPU time: a request that finishes early leaves its GPU slot idle until the longest request in the batch completes.

Continuous Batching (Orca, 2022)

Each decode step, the scheduler inserts new requests into available batch slots as existing ones complete — at token granularity, not request granularity. This keeps all GPU batch slots occupied. GPU utilisation improves from 30–50% (static) to 70–90% (continuous batching) on typical traffic distributions.

PagedAttention Memory Management

KV cache for a single request: sequence_len × n_layers × n_heads × d_head × 2 bytes For LLaMA-3 70B, max context 8K, BF16: = 8192 × 80 × 64 × 128 × 2 ≈ 10.7 GB per request at max length Static allocation: reserve max_length × KV_per_token for each request at start. Problem: most requests are much shorter than max length → wasted reserved memory. At batch=50 with max=8K: 50 × 10.7 GB = 535 GB needed — 7× an H100's capacity. PagedAttention: allocate KV cache in pages (blocks of 16 tokens). Each request grows its page table as it generates tokens. Freed at completion; pages immediately reusable. Result: supports 50+ concurrent requests on a single H100, not 5.

Prompt Prefix Caching

Many API users prepend a long system prompt to every request (e.g., "You are a customer service agent for Company X…"). Without caching, the prefill phase recomputes the KV vectors for this system prompt on every request — wasteful.

Prefix caching (implemented in vLLM, TensorRT-LLM, OpenAI's API) stores the KV cache for common prefixes. When a new request starts with a cached prefix, the stored KV tensors are reused — prefill starts mid-sequence, dramatically reducing TTFT and GPU compute:

Without prefix cache: TTFT = prefill(system_prompt + user_message) = prefill(200 tokens + 50 tokens) = prefill(250 tokens) With prefix cache hit on system_prompt: TTFT = prefill(50 tokens only) Speedup: 250/50 = 5× lower TTFT Compute saved: 80% of prefill FLOPs for that request Cache key: SHA-256 hash of tokenised prefix → maps to a set of KV pages Eviction policy: LRU (Least Recently Used) across all requests in the serving pool

Geographic Distribution

Inference latency has a physical speed-of-light floor. Light travels ~200 km/ms in fibre (with switching overhead). A user in Tokyo querying a server in Virginia adds ~75 ms one-way round-trip before the first token arrives — violating TTFT SLOs.

Inference is deployed across Points of Presence (PoPs) in major population centres. Model weights are replicated to each PoP — for a 70B model at INT4, that is 35 GB per PoP. A global deployment might have 8–12 PoPs:

Approximate network RTT by region: North America (same coast): 5–15 ms Cross-continental US: 60–80 ms US to Europe: 80–100 ms US to Asia-Pacific: 150–200 ms Target TTFT of <300 ms → PoPs needed in NA, EU, APAC at minimum. Model replication cost: 70B INT4 model: 35 GB × 10 PoPs = 350 GB of distributed storage Each PoP: 2–8 GPU pods for redundancy (16–64 H100s minimum) Global serving fleet: 100–1,000 H100s for a mid-scale consumer LLM

Traffic Routing

Anycast DNS routes users to the geographically nearest PoP. If a PoP is at capacity, requests overflow to the next-nearest. Health checks detect GPU pod failures within seconds and remove unhealthy pods from the routing pool. Blue/green deployments push model version updates to one PoP at a time, rolling forward only if metrics remain healthy.

Cost Modeling

The economics of inference determine pricing and profitability. Key cost driver: GPU hours per token.

Cost per 1M output tokens (rough estimates, 2024): H100 cloud spot price: ~$2.50–3.00/GPU-hour 70B model, TP=8: 8 GPUs per pod Decode throughput (batch=32, INT4): ~2,000 tokens/sec per pod = 7.2M tokens/hour GPU cost per 1M tokens: 8 × $2.75 / 7.2M × 1M = $3.06/M tokens Anthropic Claude 3.5 Sonnet API: $3.00/M output tokens (mid-2024) → Roughly at-cost compute for output tokens at this price level OpenAI GPT-4o: $15.00/M output tokens → ~5× markup (larger model, less efficient) GPT-4o mini: $0.60/M output → smaller model, ~5× cheaper than 70B size Groq (LPU): ~$0.27/M → specialised inference hardware, extremely efficient
Hardware choice for inference GPUs are general-purpose and dominate due to availability and software ecosystem. Purpose-built inference accelerators like Groq's LPU (Language Processing Unit) and AWS Trainium/Inferentia sacrifice training flexibility for 10–50× better tokens/watt and tokens/dollar. As model architectures stabilise, more inference will shift to fixed-function hardware.
