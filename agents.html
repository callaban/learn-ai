Agentic AI

A chatbot answers. An agent acts. This page explains what that difference really consists of — the loop, the tools, the memory, the failure modes — and what it takes for a person to direct and supervise software that makes its own moves.

Prerequisites: LLMs, Inference Reading time ~30 min Reviewed 2026

What an Agent Actually Is

In plain terms

An AI agent is a language model placed inside a loop, given a goal, and handed a set of tools it can operate. Instead of producing one answer and stopping, it decides what to do, does it, looks at the result, and decides again — until the goal is met or it gives up. Everything else on this page is detail about that loop.

The word "agent" has been stretched to cover almost anything involving a language model, which makes it nearly useless as a technical term. It is worth being precise. A useful working definition:

Definition An agent is a system in which a language model directs its own control flow: the model — not a fixed script — decides which action to take next, observes the result of that action, and repeats. The number of steps is not known in advance.

That last clause is the sharp edge of the definition. If you can draw the complete flowchart before the program runs, you have a workflow, not an agent. Workflows are frequently the better engineering choice: they are cheaper, faster, easier to test, and their failure modes are predictable. Agency is something you should pay for only when the problem genuinely requires it.

Workflow (predetermined path)

"Take the customer email → classify it into one of six categories → look up the account → draft a reply from the matching template → send it to a human for approval."

Every step is written by an engineer. The model fills in slots. Behaviour is repeatable and cheap to evaluate.

Agent (model-directed path)

"This test suite fails on the CI runner but passes locally. Find out why and fix it."

Nobody can write the flowchart in advance, because the right next step depends on what the previous step revealed. The model must decide.

The Three Ingredients

Every agent, from a fifty-line script to a production coding assistant, is assembled from the same three parts:

  1. A model capable of deciding. It must reliably choose among available actions, produce well-formed tool calls, and recognise when it has enough information to stop. This is a trained capability, not a prompting trick — see Training a Model to Be Agentic below.
  2. Tools that let it affect the world. Read a file, run a query, call an API, execute code, click a button. Without tools an agent can only think, and thinking without acting is just a longer answer.
  3. A loop with persistent context. The harness that runs tools, feeds results back, keeps a growing record of what has happened, and decides when to stop. This is ordinary software, and it is where most of the engineering effort actually goes.
An analogy

A base language model is a brilliant consultant locked in a windowless room with no phone. You can slide questions under the door and get remarkable answers back, but the consultant cannot look anything up, cannot check whether their advice worked, and cannot do anything themselves. Agent-building is the work of giving them a phone, a computer, a filing cabinet, and a clear brief — and then deciding how much you are willing to let them do without asking you first.

The Agent Loop

Strip away the frameworks and every agent reduces to the same cycle. The model is called repeatedly; each call sees the entire history of the task so far.

What the Model Actually Sees

It is worth being concrete, because the mechanism is far simpler than the vocabulary suggests. Tools are described to the model as structured schemas placed in its context. The model emits a specially formatted block requesting a call. The harness — ordinary code you control — parses it, executes the real function, and appends the result as a new message. Then the model runs again on the longer context.

Turn 1 — the harness sends the model: [system] You are a coding agent. Tools available: read_file(path: string) -> string run_shell(cmd: string) -> {stdout, stderr, exit_code} edit_file(path: string, old: string, new: string) -> ok [user] The test suite fails on CI but passes locally. Fix it. Model responds: tool_call: run_shell(cmd="pytest -x tests/ 2>&1 | tail -30") Turn 2 — the harness executes it and sends everything back, plus: [tool_result] FAILED tests/test_report.py::test_dates AssertionError: '2026-03-01' != '2026-02-28' Model responds: tool_call: read_file(path="src/report.py") Turn 3 — ... and so on. Each turn re-reads the entire growing transcript.

Three consequences fall directly out of this mechanism, and they explain most agent behaviour you will ever observe:

  • The context is the agent's memory. There is no hidden state. Anything not in the transcript effectively did not happen. If you truncate the transcript, you give the agent amnesia.
  • Cost grows superlinearly with steps. A 20-step task re-processes a growing transcript 20 times. Without prefix caching (see Inference Data Centers) the token bill for step n scales with everything that came before it.
  • Tool results are untrusted input. A web page, a code comment, a database row — anything the agent reads enters the same context as your instructions. This is the root of prompt injection, covered in How Agents Fail.
ReAct: the pattern that named the field The interleaving of reasoning and acting was formalised as ReAct (Yao et al., 2022): let the model write a thought, then an action, then observe, and repeat. It outperformed both pure chain-of-thought (which reasons but never checks reality) and pure action selection (which acts but never plans). Nearly every agent architecture since is a variation on it. Modern reasoning models fold the "thought" step into their own extended thinking rather than emitting it as visible text, but the structure is unchanged.

Training a Model to Be Agentic

In plain terms

You cannot turn any language model into a good agent with clever prompting. Being a competent agent — staying on task for fifty steps, recovering from an error, knowing when to stop — is a skill that has to be trained in, and the training method that produces it is reinforcement learning against tasks that can be automatically graded.

Pretraining (covered on the Training page) teaches a model to predict text. That produces knowledge and fluency, but not the ability to pursue a goal over many steps. Agentic competence comes from post-training, and the decisive ingredient has been reinforcement learning from verifiable rewards (RLVR).

The idea is simple and powerful. Take tasks where success can be checked by a program rather than a human: does the code compile, do the tests pass, is the maths answer correct, did the agent reach the target page. Let the model attempt the task thousands of times, and reinforce the trajectories that succeeded. No human labeller is in the loop, so the process scales with compute rather than with human hours — which is exactly the property that lets a capability improve quickly.

Why verifiable rewards changed agents Human preference RL (RLHF): reward = "which answer do people prefer?" → teaches style, helpfulness, tone → bounded by how fast humans can label Verifiable-reward RL (RLVR): reward = "did the tests pass? y/n" → teaches persistence, error recovery, tool use → bounded only by compute and task supply The hard part is credit assignment: a 40-step trajectory earns one reward at the end. Which of the 40 decisions deserves the credit? Algorithms such as PPO and GRPO handle this by comparing whole trajectories against each other rather than scoring steps individually.

This is also why reasoning models — models trained to spend extra computation thinking before answering — were the unlock for practical agents. An agent's most expensive mistake is choosing a bad action early and then spending thirty steps in the wrong part of the search space. A model that can deliberate before acting makes materially fewer of those errors, and the deliberation is cheap relative to the wasted actions it prevents.

The doubling that matters The most useful single metric for agent progress is not benchmark accuracy but task horizon: the length of task, measured in how long a skilled human would take, that a model can complete unaided at a given success rate. Measured this way, frontier model capability has been roughly doubling every few months — from tasks of a few minutes in 2023 to multi-hour tasks by 2025–26. If that trend holds even approximately, the interesting question stops being "can the model do this?" and becomes "how do I verify a day's worth of work I did not watch happen?" That question is the subject of the human's job, below.

Anatomy of an Agent System

A production agent is mostly conventional software wrapped around a model call. Here is the full parts list.

Tools: the Interface to Reality

Tool design is the highest-leverage work in agent building, and it is closer to API design for a capable but literal-minded new colleague than to traditional programming. Four families dominate:

KindHow it worksStrengthsCosts
Function callingTyped schemas the model fills in; the harness dispatchesPrecise, fast, auditable, easy to permissionSomeone must write and maintain each tool
MCP serversThe Model Context Protocol — an open standard, released by Anthropic in late 2024 and now broadly adopted, that lets any application expose tools, resources and prompts to any agent over a common interfaceWrite the connector once, use it from every agent; a real ecosystem of pre-built serversEach connected server consumes context and enlarges the trust boundary
Code executionThe model writes code that runs in a sandboxMaximum expressiveness; the agent composes its own operations and processes data without pulling it all into contextRequires genuine isolation; hardest to constrain
Computer useThe model sees screenshots and emits clicks and keystrokesWorks with software that has no API at all — the universal fallbackSlow, expensive per step, brittle to UI changes, error-prone
Rules of thumb for tool design
  • Few and sharp beats many and vague. Forty overlapping tools produce selection errors. Consolidate.
  • Return what helps the next decision. A 40,000-token API dump burns context and buries the signal. Filter, paginate, summarise at the tool boundary.
  • Make errors instructive. Error: invalid date_range. Expected ISO-8601, e.g. "2026-01-15". Got "last Tuesday". An agent can act on that. Error 400 teaches it nothing.
  • Name things for a stranger. The model has no institutional context. get_active_subscriptions is obvious; fetch_sub_v2 is a guessing game.
  • Prefer idempotence, and be explicit about what is not. Retries happen. Make it safe when they do — and gate the actions where it isn't.

Context Engineering

In plain terms

An agent's context window is a desk. Everything the agent can currently use has to fit on it. The craft of agent building is largely deciding, at each step, what belongs on the desk — because a cluttered desk makes an agent stupid just as reliably as a bad model does.

"Prompt engineering" was about phrasing a single request well. Context engineering is about curating an evolving working set across dozens of steps, and it is the discipline that separates agents that work from agents that demo. Context windows have grown enormously — hundreds of thousands of tokens is routine, a million is available — but capacity is not the constraint that matters.

Context rot: bigger is not better Model performance degrades as context fills, well before the limit is reached. Attention is a finite resource being divided among more tokens; irrelevant material actively competes with relevant material. A model given 200,000 tokens of "everything that might be useful" often performs worse than the same model given 15,000 tokens of carefully selected material. Treat context as a budget to be spent deliberately, not a bucket to be filled.

Techniques That Actually Move the Needle

  • Compaction. When the transcript approaches its budget, summarise the older portion — decisions made, files touched, facts established, what remains — and continue from the summary. Done well, an agent can run for hours across many compactions. Done badly, it forgets the constraint that mattered and cheerfully redoes work it already did.
  • Retrieval over preloading. Do not paste the codebase in. Give the agent grep, find and file reads and let it pull what it needs, when it needs it. Just-in-time retrieval keeps the desk clear and, as a bonus, mirrors how a human would actually work.
  • Externalised memory. Let the agent write notes, plans, and intermediate results to files. A to-do file that survives compaction is a startlingly effective memory mechanism, and it doubles as a progress display for the human watching.
  • Sub-agents for exploration. Delegate a search-heavy subtask to a fresh agent with its own clean context; it returns a short answer instead of the 80,000 tokens of dead ends it waded through. The parent's context stays clean.
  • Structured note-taking. Ask the agent to maintain an explicit state document — hypothesis, evidence, next action. This makes reasoning inspectable by the human and resilient to truncation.
A context budget for a long coding task (200K window) System prompt + role ~2K stable, cached Tool schemas (12 tools) ~4K stable, cached Project conventions file ~3K stable, cached ──────────────────────────────────────────────── Cached prefix ~9K → ~10× cheaper per token on reuse Task statement ~1K Retrieved file contents (4 files) ~18K churns as work moves Running transcript (28 steps) ~60K grows every step Working notes / to-do file ~2K ──────────────────────────────────────────────── Live total ~90K compact at ~140K, keep going
Why prefix caching is an agent's best friend Keep the unchanging part of your context — system prompt, tool schemas, conventions — at the very front and byte-identical between calls. Inference servers cache the attention state for that prefix, so re-reading it on step 40 costs a fraction of what it cost on step 1. Reorder or edit that prefix mid-run and you invalidate the cache, quietly multiplying your bill. This single detail can move the cost of a long agent run by an order of magnitude.

Multi-Agent Systems

Once one agent works, the obvious move is several. Sometimes that is right; often it is expensive theatre. The useful question is not "how many agents?" but "does this subtask deserve its own context window?"

Orchestrator–worker

A lead agent decomposes the task and dispatches subtasks to workers, each with a clean context. Workers report back concise findings.

Works well for research, broad codebase search, and anything with independent parallel branches.

Pipeline

Specialised agents in sequence: draft → critique → revise → verify. Each stage sees only what it needs.

Works well when quality gates are genuinely separable and each stage has a clear rubric.

Debate / ensemble

Several agents attempt the same problem independently; a judge selects or synthesises.

Use sparingly — real gains on hard reasoning, but N× the cost for often modest improvement.

The coordination tax Agents communicate through natural language, which is a lossy channel. Every hand-off risks dropping a constraint the sender considered obvious. Worse, sub-agents cannot see each other's work, so two of them will happily edit the same file in incompatible ways. A rough guide: parallelise reading aggressively — many agents searching, analysing, and reporting back is close to free parallelism. Parallelise writing only with explicit ownership boundaries, or expect to spend your savings on merge conflicts. And a single agent with a well-managed context beats five agents with muddled ones almost every time.

How Agents Fail

In plain terms

The way agents fail is different from the way chatbots fail, and more consequential. A chatbot's mistake is a wrong sentence you can read and discard. An agent's mistake is a wrong action — a deleted file, a sent email, a merged pull request — and it may be the foundation for twenty more actions before anyone notices.

Error Compounding

This is the arithmetic that governs agent reliability, and it is unforgiving:

Probability a whole task succeeds = (per-step reliability)^(number of steps) Steps: 5 10 20 50 ──────────────────────────────────────────────── 95% / step 77% 60% 36% 8% 99% / step 95% 90% 82% 61% 99.9% / step 99.5% 99% 98% 95% Reliability compounds against you. This is why the engineering effort goes into error recovery, not just error prevention: a step that fails and is correctly diagnosed and retried is not a lost step. Checkpoints, verification steps, and tools that fail loudly and informatively are what convert 95% into something usable.

Prompt Injection and the Lethal Trifecta

This deserves its own treatment because it is the security problem unique to agents, and because it does not have a clean solution. Recall the mechanism: tool results enter the same context as your instructions. A model reading a web page cannot reliably distinguish "content I was asked to summarise" from "instructions addressed to me." A comment in a GitHub issue, a line in a CSV, alt text in an image — any of it can carry an instruction.

The lethal trifecta An agent becomes genuinely dangerous when it simultaneously has all three of:
  1. Access to private data — your repository, your email, your database;
  2. Exposure to untrusted content — the open web, inbound messages, third-party files;
  3. The ability to communicate externally — send, post, push, call an API.
With all three, injected text can instruct the agent to read a secret and exfiltrate it, and the agent will comply, because from inside the context it looks like a legitimate request. Break any one leg and the attack fails. That is the practical defence: no network egress in a sandbox with credentials; no credentials in a sandbox with network egress; human approval on the boundary where the trifecta would otherwise close.

Defences that help but do not solve it: clearly delimiting untrusted content in the context, training models to treat tool output as data rather than instruction, classifiers on inputs and outputs, and — most reliably — keeping the agent's permissions narrow enough that a fully compromised agent still cannot do much harm. Design as if injection will eventually succeed, because eventually it will.

Check yourself

An agent runs 30 steps at 97% per-step reliability. What is the chance the whole task succeeds?

0.97³⁰ ≈ 40%. Which is why per-step reliability alone is the wrong thing to optimise — recovery, verification and checkpointing matter more than shaving the last percent off any single step.

Your agent reads GitHub issues and can push commits. Which leg of the lethal trifecta would you break, and how?

Untrusted content (issues) is essential to the task and private data (the repo) is the point, so break external communication: let the agent push only to a scratch branch that requires human review before it can merge or deploy. The blast radius of a successful injection becomes "a branch nobody merged."

Why might giving an agent a 1M-token context make it perform worse than a 50K one?

Context rot. Attention is spread across more tokens, and irrelevant material competes with relevant material. The useful move is better curation, not more capacity.

Working with Agents: the Human's Job

In plain terms

Working with agents is much closer to delegating to a fast, capable, literal-minded colleague who has no idea how your organisation works than it is to using a tool. The skills that matter are the ones good managers already have: writing a clear brief, choosing what to delegate, and verifying results without redoing the work.

Write the Brief Properly

The single largest determinant of agent output quality is the quality of the request. Agents fail on ambiguity far more often than on difficulty. A good brief contains:

  1. The goal, and why. "Add caching to the report endpoint because it times out for accounts with over 10,000 rows" lets the agent choose sensibly. "Add caching" invites a guess.
  2. The boundaries. What it may change, what it must not touch, what it should ask about rather than decide. Scope creep is the default behaviour of a capable and eager worker.
  3. The definition of done. Ideally something checkable: tests pass, the endpoint responds in under 200 ms, the report matches this fixture. Verifiable goals are also better goals for the agent to steer by.
  4. The context it cannot infer. Conventions, prior decisions, the reason the obvious approach was rejected last time. Write this down once in a project file — CLAUDE.md, AGENTS.md, a README section — rather than retyping it every session.

Calibrate Trust to Blast Radius

The right level of autonomy is not a property of the agent; it is a property of the consequences. A sensible ladder:

LevelHuman involvementAppropriate when
1 · SuggestAgent proposes, human performs every actionLearning a new agent; high-stakes or regulated systems
2 · Approve each actionAgent acts, human confirms every tool callProduction data; anything irreversible
3 · AllowlistReads and safe commands run freely; writes, deletes and network calls promptThe everyday default for most development work
4 · Sandbox autonomyAgent runs freely inside an isolated container; human reviews the final diffWell-scoped tasks with an easy revert path and no live credentials
5 · UnattendedAgent runs on a schedule or trigger; human reviews outcomes and metricsNarrow, well-evaluated, thoroughly instrumented tasks only
The verification bottleneck — the real limit on agent usefulness An agent can produce four hours of work in twenty minutes. If checking it takes three hours, you have gained very little; if you skip the check, you have accepted unreviewed work into your system. As generation gets cheaper, verification becomes the scarce resource, and the highest-leverage engineering investment shifts accordingly: better tests, better types, better linters, better staging environments, smaller diffs, richer traces. Teams that invest in making work cheap to check get compounding returns from agents. Teams that only invest in prompting hit a ceiling almost immediately — and it is a ceiling made of their own review capacity.

Make Your Environment Agent-Legible

Agents work far better in environments built for them, and — pleasingly — the changes are the same ones that help new human colleagues:

  • A fast, reliable test suite. The agent's feedback loop and your verification mechanism, in one. Flaky tests are actively corrosive: they teach the agent that failures are noise.
  • A conventions file at the project root. How to run things, what not to touch, the decisions already made. Load-bearing documentation.
  • Reproducible setup. If a human needs three days of tribal knowledge to get a working environment, the agent will fail in the first five minutes.
  • Small, reviewable units of work. One task, one branch, one diff you can actually read.
  • Machine-readable interfaces. A CLI or API beats a GUI; explicit errors beat silent failure; types beat comments.

Managing Agents in Production

An agent deployed for real users is a distributed system with a stochastic component, and it needs the operational apparatus that implies.

Observability

When an agent misbehaves, "the model was wrong" is almost never the actual cause. It is a truncated context, a tool that returned an unhelpful error, a permission denial the model interpreted as a missing file. You cannot diagnose any of that without a full trace: every prompt, every tool call, every result, with token counts, latency and cost attached to each step. Build this before you need it — the first production incident is a bad time to discover you are logging nothing.

Evaluation

Agent evaluation differs from model evaluation because the output is a trajectory, not a string. Three layers, in increasing order of what they cost you:

  • Outcome evals. Did the task succeed, judged by a program? Cheap, objective, and the backbone of any regression suite.
  • Trajectory evals. Did it get there sensibly — reasonable number of steps, no dangerous actions, no reward hacking? Catches agents that pass for the wrong reasons.
  • Human review of samples. Expensive, irreplaceable, and the only thing that reliably catches the failure mode nobody thought to write an eval for.

The Evaluation & Benchmarks page covers the methodology, including why public agent benchmarks tend to overstate real-world performance.

Identity, Authorisation, and Audit

An agent acting on your behalf raises questions that ordinary software does not. Whose credentials does it use? If it acts at 3 a.m. under a service account, who is accountable for the action? What does the audit log record — the agent, the human who launched it, or both?

The emerging good practice is to treat each agent as a first-class principal: its own identity, its own narrowly scoped and short-lived credentials, its own entry in the audit log, and a recorded link to the human or system that authorised the run. "The agent used my API key" is a governance failure waiting for an incident report to be written about it. This is also where agent engineering meets the regulatory material on the Safety & Governance page — accountability frameworks generally require exactly this kind of traceability.

Where This Is Going

Forecasting in this field ages badly, so treat the following as informed extrapolation, not prediction. The direction of travel, as of 2026:

  • Established Agents are the default product form

    Coding assistants that edit repositories and run tests, research agents that browse and synthesise, and customer-facing agents that transact are shipped products, not demos. Tool use and reasoning are assumed capabilities of frontier models rather than differentiators.

  • Underway Standardised plumbing

    MCP has made tool connectivity roughly as portable as HTTP made document retrieval. The comparable work now happening in agent identity, payment authorisation and inter-agent communication is less mature, and the standards contest is unresolved.

  • Underway Longer horizons, higher stakes

    As reliable task horizons stretch from minutes to hours to days, the binding constraint moves decisively from model capability to verification, permissioning and organisational trust. The interesting engineering problems become social and procedural as much as technical.

  • Projected Fleets, and the management problem

    Running dozens of concurrent agents makes individual supervision impossible and forces a shift to managing by outcome, sampling and exception — the same transition an organisation makes when it grows past the size where one person can watch everything. Expect the tooling for this to look more like operations dashboards than like chat.

  • Projected Economic agents

    Agents holding budgets, negotiating, and transacting with other agents raise unsettled questions of liability, fraud and market structure. The technology will arrive before the legal framework does; it usually does.

A provocation worth sitting with Every argument for agent autonomy is an argument about who checks the work. We accept unverified output from human professionals constantly — we do not re-derive our doctor's reasoning — because we have centuries of institutional scaffolding for it: licensure, liability, reputation, malpractice insurance. None of that scaffolding exists for agents yet. The technical question "can the agent do this task?" is being answered rather quickly. The question "under what circumstances should anyone accept the result without checking?" has barely been posed, and it is the one that will actually determine how far this goes.

Key takeaways

  • An agent is a model in a loop with tools, where the model — not a script — decides the next step. If you can draw the flowchart in advance, build a workflow instead; it will be cheaper and more reliable.
  • The context window is the agent's entire memory. Curating it is the central engineering craft, and more context is not better context.
  • Agentic competence is trained, chiefly through reinforcement learning on automatically verifiable tasks — which is why progress here scales with compute rather than with human labelling.
  • Reliability compounds against you across steps, so invest in error recovery and verification, not just in preventing individual mistakes.
  • Prompt injection is structural, not a bug. Break the lethal trifecta — private data, untrusted content, external communication — rather than hoping to filter your way out.
  • The binding constraint on agent usefulness is human verification capacity. Making work cheap to check pays better than making the agent slightly smarter.
