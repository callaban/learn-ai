Infrastructure

Data Centers for AI Training

Training frontier models requires clusters of 10,000–100,000 GPUs linked by specialised low-latency fabrics, sustained by hundreds of megawatts of power, and cooled by liquid or immersion systems. This page covers the engineering of those systems end to end.

Scale of Compute Required

Training a frontier LLM requires an amount of compute that dwarfs any other computation in history. Using the Chinchilla formula C ≈ 6PD:

GPT-4 (estimated): P ≈ 1.8T params, D ≈ 13T tokens C ≈ 6 × 1.8×10¹² × 13×10¹² ≈ 1.4×10²⁶ FLOPs Training cluster: 25,000 NVIDIA A100 80GB GPUs A100 BF16 tensor core throughput: 312 TFLOPS Cluster peak: 25,000 × 312 × 10¹² = 7.8 × 10¹⁸ FLOPS At 35% MFU: effective = 2.7 × 10¹⁸ FLOPS Training time: 1.4×10²⁶ / 2.7×10¹⁸ ≈ 5.2×10⁷ seconds ≈ 600 days Real GPT-4 training: estimated ~3 months → MFU was higher, or cluster was larger.

Intra-Node Interconnects: NVLink

Within a single server, multiple GPUs must exchange gradient tensors with extremely high bandwidth. PCIe (the standard CPU-GPU interface) tops out at 64 GB/s bidirectional — far too slow for distributed training. NVIDIA's NVLink is a proprietary GPU-to-GPU interconnect:

GenerationGPUTotal BandwidthLinks per GPU
NVLink 3.0A100600 GB/s bidirectional12 links × 25 GB/s
NVLink 4.0H100900 GB/s bidirectional18 links × 25 GB/s
NVLink 5.0B2001,800 GB/s bidirectional18 links × 50 GB/s

An NVIDIA DGX H100 server contains 8 H100 GPUs connected in an NVSwitch-based all-to-all fabric. Any GPU can communicate with any other GPU at full NVLink speed simultaneously:

DGX H100 NVLink bisection bandwidth: 8 GPUs × 900 GB/s = 7.2 TB/s aggregate NVSwitch bandwidth Compare to PCIe Gen5 x16: 64 GB/s → 14× slower than NVLink 4.0 All-reduce bandwidth on a DGX node (ring algorithm): Effective all-reduce BW = n-1/n × NVLink BW per GPU For n=8: 7/8 × 900 = 787 GB/s

The NVSwitch chip is a dedicated crossbar switch. A DGX H100 contains 4 NVSwitch chips, each providing 13.6 TB/s of switch bandwidth. The total switch capacity (54.4 TB/s) far exceeds the aggregate NVLink GPU bandwidth (7.2 TB/s), ensuring non-blocking all-to-all communication at full speed.

Inter-Node Interconnects: InfiniBand

Communication between servers uses InfiniBand (IB), a high-speed low-latency network protocol purpose-built for HPC clusters. Ethernet is used in cloud data centres but has higher latency and lower efficiency for collective communications.

IB GenerationPer-Port BandwidthTypical ConfigLatency
HDR (2019)200 Gb/s25 GB/s per port~0.6 μs
NDR (2022)400 Gb/s50 GB/s per port~0.5 μs
XDR (2025)800 Gb/s100 GB/s per port~0.4 μs

Each DGX H100 server has 8 IB network cards (one per GPU, via an NVLink-IB bridge called ConnectX). With NDR, each server has 8 × 400 Gb/s = 3.2 Tb/s of total external bandwidth — needed to match the NVLink bandwidth available within the node for inter-node gradient synchronisation.

RDMA: Remote Direct Memory Access

InfiniBand uses RDMA — one GPU can read or write data directly into another GPU's HBM across the network without involving either server's CPU. This eliminates PCIe and CPU bottlenecks:

Traditional network: GPU → PCIe → CPU → NIC → network → CPU → PCIe → GPU RDMA path: GPU → NVLink → NIC → network → NIC → GPU Latency saved: 2× CPU + 2× PCIe crossings ≈ 5–10 μs eliminated RDMA latency: 600 ns–1 μs (vs 50–100 μs for TCP/IP)

All-Reduce in Practice

During data-parallel training, all GPUs must sum their gradient tensors and distribute the result. The NCCL library (NVIDIA Collective Communications Library) implements ring-all-reduce on top of NVLink and IB:

Ring all-reduce on N GPUs, data size S: Phase 1 (Reduce-Scatter): each GPU sends/receives S/N data in N-1 steps Phase 2 (All-Gather): each GPU broadcasts its reduced chunk in N-1 steps Total data moved per GPU: 2(N-1)/N × S ≈ 2S bytes Time: 2S/B where B = bandwidth per link For N=1024 GPUs, S=280GB (70B params in FP32 gradients): → 2 × 280 / 50 GB/s (IB NDR) = 11.2 seconds per all-reduce → This dominates training iteration time for poorly configured clusters

Storage: Parallel File Systems

Training data must be fed to GPUs fast enough to keep them busy. A single H100 processes ~16,000 tokens/second. A 10,000-GPU cluster processes 160 million tokens/second — 320 MB/s of tokenised data. The storage system must sustain far higher rates to allow checkpointing and data shuffling.

Production training uses distributed parallel file systems:

  • IBM GPFS (Spectrum Scale): Stripes files across hundreds of storage nodes. Aggregate throughput of 1–10 TB/s. Used in many HPC and AI clusters.
  • Lustre: Open-source parallel file system, common in academic and national lab supercomputers. Separates metadata (MDS) from data (OSS) servers.
  • WekaFS: All-NVMe parallel file system optimised for AI. Delivers high IOPS and throughput from NVMe SSDs over RDMA.

Checkpointing (saving model weights, optimizer state, and training state) is critical for fault recovery on long training runs. A 70B model checkpoint (FP32 weights + Adam state) is ~1.1 TB. Checkpointing every 30 minutes to a parallel file system requires writing at ~600 MB/s — well within GPFS capabilities. Some clusters keep recent checkpoints in RAM (CPU DRAM acts as a checkpoint buffer).

Power and Cooling

Power Density

H100 SXM5 TDP: 700W DGX H100 (8× H100 + 2× Intel Xeon + networking): ~10.2 kW per server 42U rack with 10 DGX servers: ~102 kW per rack Traditional data centre rack limit: 10–15 kW/rack AI cluster rack limit: 100–200 kW/rack (liquid-cooled) 10,000-GPU cluster: 10,000/8 = 1,250 servers × 10.2 kW = 12.75 MW compute power + networking, storage, cooling overhead (PUE 1.2–1.4): Total facility power: ~15–18 MW for 10,000 GPUs 100,000 GPU cluster (xAI): ~120–150 MW

Cooling Technologies

Air Cooling

High-CFM fans draw cool air through server front, exhaust hot air through rear. Traditional data centres manage 15–20 kW/rack with hot-aisle/cold-aisle containment. At 100 kW/rack densities required for H100, airflow velocities and noise become impractical. Air cooling is the fallback, not the choice, for AI clusters.

Direct Liquid Cooling (DLC)

Water is routed directly to cold plates on GPUs and CPUs. The NVIDIA DGX H100 supports rear-door heat exchangers and direct liquid cooling. Water absorbs 5× more heat per unit volume than air. Allows 100+ kW/rack. Coolant outlet temperature can be 40–60°C — warm enough to use waste heat for building heating.

Immersion Cooling

Entire servers are submerged in non-conductive dielectric fluid (mineral oil or engineered fluids like 3M Novec). Fluid circulates, carrying heat to a heat exchanger. Eliminates fans entirely. Achieves PUE of 1.02–1.05 (near-perfect efficiency). Servers must be modified to remove fans; standard HDD-based storage cannot be submerged. Used by some hyperscale AI facilities.

Power Usage Effectiveness (PUE)

PUE = Total Facility Power / IT Equipment Power. PUE = 1.0 is perfect (all power goes to compute). Air-cooled: 1.3–1.5. DLC: 1.1–1.2. Immersion: 1.02–1.05. For a 70 MW cluster, the difference between PUE 1.5 and 1.05 is 31.5 MW of wasted cooling power — equivalent to a small power plant.

Power Sources

A 150 MW AI training facility exceeds the capacity of a typical city substation. Operators increasingly co-locate with power generation:

  • xAI Memphis: Powered initially by natural gas turbines on-site; transitioning to grid. 150 MW planned capacity.
  • Microsoft/OpenAI: Exploring dedicated nuclear plant construction (SMRs) for the multi-GW scale needed for GPT-5 and beyond.
  • Google: Signed the first-ever corporate Power Purchase Agreement for advanced nuclear (Kairos Power, 2024).

Fault Tolerance on Long Training Runs

A training run on 10,000+ GPUs over 3 months has an extremely high probability of hardware failure. GPU failure rates are ~0.1–1% per month per GPU; on 10,000 GPUs, expect 10–100 failures per month. Training frameworks must:

  • Checkpoint frequently — every 10–30 minutes, writing model state to parallel storage. On failure, resume from the last checkpoint.
  • Elastic training — gracefully shrink the cluster after a failure, continue training on N-1 nodes, and add a replacement GPU when available.
  • Async checkpointing — write checkpoint to CPU DRAM (fast) while GPU continues training; flush to disk in parallel.
  • Health monitoring — per-GPU telemetry (temperature, error-correcting code corrections, PCIe errors) triggers preemptive replacements before outright failure.
