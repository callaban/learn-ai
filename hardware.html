Hardware

AI Hardware: The Silicon Behind Intelligence

From CPU cores to tensor cores, from DRAM to HBM3e, from PCIe to NVLink — the full hardware stack that makes billion-parameter model training and inference possible, and why each component's design decisions cascade up the entire software stack.

Why CPUs Cannot Train AI Models

A modern server CPU (e.g. Intel Xeon Platinum 8592+) has 64 cores running at 3.9 GHz with AVX-512 SIMD units. AVX-512 can process 16 float32 values simultaneously per core. Total FP32 throughput:

64 cores × 2 (FMA) × 16 floats × 3.9 GHz = ~8 TFLOPS peak FP32 NVIDIA H100 SXM5: 66.9 TFLOPS FP32, 1,979 TFLOPS BF16 (tensor cores) Ratio: ~250× more TFLOPS on GPU vs high-end CPU Core count: CPU: 64 powerful cores optimised for serial, branch-heavy code H100: 16,896 CUDA cores + 528 Tensor Core units Memory bandwidth: CPU (DDR5-4800, 8-channel): 8 × 4800 MT/s × 8B = 307 GB/s H100 SXM5 (HBM3): 3,350 GB/s → 11× more bandwidth

Neural network training consists almost entirely of matrix multiplications — the GEMM (General Matrix Multiply) operation: C = A × B. GEMM is embarrassingly parallel: every element of C can be computed independently, making it ideal for thousands of simple parallel cores. CPUs are over-engineered for this: their complex out-of-order execution engines, large caches, and branch predictors all add transistor cost that contributes nothing to GEMM throughput.

GPU Architecture

SIMT Execution Model

A GPU executes threads in groups of 32 called warps. All 32 threads in a warp execute the same instruction simultaneously on different data — Single Instruction, Multiple Thread (SIMT). This is highly efficient when all threads follow the same code path. Branch divergence (threads taking different if/else paths) serialises execution, reducing throughput by up to 32×.

H100 SM (Streaming Multiprocessor) count: 132 SMs Each SM contains: - 128 FP32 CUDA cores - 4 Tensor Core units (4th gen) - 256 KB register file - 228 KB L1 cache / shared memory (configurable) - 4 warp schedulers (issue 1 instruction/warp/cycle) Maximum resident warps per SM: 64 Maximum resident threads per SM: 2,048 Total CUDA cores: 132 × 128 = 16,896 Total Tensor Core units: 132 × 4 = 528

Tensor Cores

Tensor Cores are specialised matrix-multiply-accumulate (MMA) units introduced in NVIDIA Volta (2017). They compute D = A × B + C on 16×16 or 8×16 matrices in a single operation, far faster than using CUDA cores for the same computation:

H100 4th-gen Tensor Core operation (per cycle per unit): Input: A ∈ ℝ^{16×8} (BF16), B ∈ ℝ^{8×16} (BF16) Output: D ∈ ℝ^{16×16} (FP32) FLOPs: 16×16×8 × 2 (mul+add) = 4,096 FLOPs per MMA per cycle Total Tensor Core throughput (BF16 → FP32, H100): 528 units × 4,096 FLOPs × 1.8 GHz boost clock ≈ 3.9 PFLOPS (Measured/published: 1,979 TFLOPS — reflects actual achievable with memory limitations) FP8 Tensor Core throughput (H100): 3,958 TFLOPS → 2× BF16 INT8 Tensor Core throughput (H100): 3,958 TOPS

Blackwell Architecture (B200)

The B200 (2025) introduces a dual-die design — two Blackwell GPU dies connected via NVLink with 1.8 TB/s die-to-die bandwidth. Together they function as a single logical GPU:

B200 SXM: - 2× Blackwell dies per package (connected via 10 TBs NVLink-C2C) - 192 GB HBM3e across 8 stacks (24 GB per stack) - Memory bandwidth: 8,000 GB/s (2.4× H100) - FP4 Tensor Core: 20 PFLOPS peak - FP8 Tensor Core: 9 PFLOPS peak (vs 3.96 for H100) - GB200 NVL72 rack: 36 Grace CPU + 72 B200 GPU modules → 1,440 TB/s NVLink fabric within a rack → 720 GB/s per B200 of NVLink bandwidth

TPU Architecture vs GPU

GPU (H100)

Many parallel SIMT cores (16,896). Large SRAM L2 cache (50 MB). Flexible: handles diverse computation graphs, branchy code, variable-length operations. Rich software ecosystem (CUDA, 3,000+ libraries). Requires skilled kernel programmers for peak performance. Memory in external HBM stacks.

TPU (v5p)

Systolic array matrix engine — data flows through an array of multiply-accumulate units like water through a grid. Extremely efficient for fixed GEMM shapes. Simpler control logic → more die area for MACs. Inter-chip interconnect (ICI) is on-chip, not via PCIe. Less flexible: dynamic shapes and control flow are expensive. Optimised for XLA (JAX/TensorFlow), not CUDA.

TPU Systolic Array

A systolic array computes C = A × B by streaming A and B through an array of PEs: Example: 128×128 systolic array Row i of A flows rightward through row i of PEs. Column j of B flows downward through column j of PEs. PE(i,j) accumulates: C(i,j) += A(i,k) × B(k,j) as data pulses through. After 128 cycles: entire 128×128 matrix product is computed. No random memory access needed — data is delivered rhythmically. This regularity makes the TPU extremely area and power efficient for GEMM.

Memory Hierarchy

Every GPU operation navigates a memory hierarchy. Bandwidth and capacity trade off at every level:

High Bandwidth Memory (HBM)

Conventional GDDR memory (used in gaming GPUs) achieves 500–700 GB/s by using many narrow channels at high frequency. HBM takes a different approach: stack multiple DRAM die vertically and connect them through-silicon vias (TSVs):

HBM3 structure (one stack): - 12 DRAM die stacked vertically (12-Hi) - Connected by TSVs (through-silicon vias): ~10,000 vias per stack - 1,024-bit wide bus (LPDDR5: 64-bit; DDR5: 64-bit; HBM3: 1024-bit!) - Per-stack bandwidth: 819 GB/s at 6.4 Gbps/pin - H100 has 6 HBM3 stacks: 6 × 819 = 4,914 GB/s raw → ~3,350 GB/s actual The HBM stack sits adjacent to the GPU die on a silicon interposer (CoWoS packaging). The short, wide bus (TSV) is the key: it's like replacing one narrow pipe with 1,024 parallel pipes. Power per bit transferred: ~3× lower than GDDR (short distance, lower voltage). HBM evolution: HBM1 (2015): 128 GB/s per stack HBM2 (2016): 256 GB/s HBM2e (2019): 460 GB/s (A100 uses 6 stacks = 2,000 GB/s) HBM3 (2022): 819 GB/s (H100) HBM3e (2024): 1,200 GB/s per stack (H200/B200 use 8 stacks)

The CUDA Software Stack

CUDA (Compute Unified Device Architecture), introduced by NVIDIA in 2006, is the programming model and runtime that makes GPUs programmable for general compute. It is the primary reason NVIDIA dominates AI — AMD's ROCm and Intel's oneAPI are years behind in ecosystem maturity.

CUDA Programming Model

CUDA thread hierarchy: Thread: single execution unit, has private registers Warp: 32 threads, executed in lockstep (SIMT) Block: up to 1,024 threads, share L1/SRAM, synchronise cheaply Grid: many blocks, distributed across all SMs automatically A CUDA kernel (GPU function) is written once and launched on a grid. The CUDA runtime schedules blocks to available SMs. Example: Matrix multiplication kernel for C = A × B Launch grid: (M/32, N/32) blocks Each block: 32×32 threads computing a 32×32 tile of C Shared memory: load A-tile and B-tile into SRAM, reuse many times → Reduces HBM accesses by factor of 32 (tile size) → This tiling is why GPU matrix multiply can approach theoretical peak throughput

Occupancy and Efficiency

Occupancy = active warps / maximum resident warps Higher occupancy hides latency: while one warp waits for memory, the SM switches to another warp instantly (zero context-switch cost). Occupancy limited by: - Register usage: 256K registers/SM, if kernel uses 128 registers/thread: max threads = 256K/128 = 2,048 → full occupancy - Shared memory: 228KB/SM, if kernel uses 50KB/block: max blocks = 228/50 = 4 blocks × 1,024 threads = 4,096 threads → 2× oversubscribed, fine - Instruction throughput: if compute-bound, occupancy above 50% gives diminishing returns

Why AMD Cannot Displace NVIDIA

AMD's ROCm provides CUDA-equivalent APIs (HIP — Heterogeneous Interface for Portability), and MI300X has competitive raw specs (192 GB HBM3, 5.3 TB/s bandwidth). The barrier is software: PyTorch, TensorRT, cuDNN, and thousands of operator kernels are deeply optimised for CUDA. Porting and re-optimising this ecosystem takes years. MI300X achieves ~80% of H100 performance on standard benchmarks but lags on custom operations that rely on NVIDIA-specific kernel tuning. The gap is narrowing but NVIDIA's ecosystem moat is substantial.
