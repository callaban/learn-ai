Hardware

AI Hardware: The Silicon Behind Intelligence

From CPU cores to tensor cores, from DRAM to HBM3e, from PCIe to NVLink — the full hardware stack that makes billion-parameter model training and inference possible, and why each component's design decisions cascade up the entire software stack.

Why CPUs Cannot Train AI Models

In plain terms

A CPU is a small team of brilliant generalists who can each solve any problem, one careful step at a time. A GPU is an army of tens of thousands of specialists who can only do arithmetic, but all at once. Training a neural network is billions of identical multiplications with no decisions to make — exactly the wrong job for the generalists and exactly the right one for the army.

A modern server CPU (e.g. Intel Xeon Platinum 8592+) has 64 cores running at 3.9 GHz with AVX-512 SIMD units. AVX-512 can process 16 float32 values simultaneously per core. Total FP32 throughput:

64 cores × 2 (FMA) × 16 floats × 3.9 GHz = ~8 TFLOPS peak FP32 NVIDIA H100 SXM5: 66.9 TFLOPS FP32, 1,979 TFLOPS BF16 (tensor cores) Ratio: ~250× more TFLOPS on GPU vs high-end CPU Core count: CPU: 64 powerful cores optimised for serial, branch-heavy code H100: 16,896 CUDA cores + 528 Tensor Core units Memory bandwidth: CPU (DDR5-4800, 8-channel): 8 × 4800 MT/s × 8B = 307 GB/s H100 SXM5 (HBM3): 3,350 GB/s → 11× more bandwidth

Neural network training consists almost entirely of matrix multiplications — the GEMM (General Matrix Multiply) operation: C = A × B. GEMM is embarrassingly parallel: every element of C can be computed independently, making it ideal for thousands of simple parallel cores. CPUs are over-engineered for this: their complex out-of-order execution engines, large caches, and branch predictors all add transistor cost that contributes nothing to GEMM throughput.

GPU Architecture

SIMT Execution Model

A GPU executes threads in groups of 32 called warps. All 32 threads in a warp execute the same instruction simultaneously on different data — Single Instruction, Multiple Thread (SIMT). This is highly efficient when all threads follow the same code path. Branch divergence (threads taking different if/else paths) serialises execution, reducing throughput by up to 32×.

H100 SM (Streaming Multiprocessor) count: 132 SMs Each SM contains: - 128 FP32 CUDA cores - 4 Tensor Core units (4th gen) - 256 KB register file - 228 KB L1 cache / shared memory (configurable) - 4 warp schedulers (issue 1 instruction/warp/cycle) Maximum resident warps per SM: 64 Maximum resident threads per SM: 2,048 Total CUDA cores: 132 × 128 = 16,896 Total Tensor Core units: 132 × 4 = 528

Tensor Cores

Tensor Cores are specialised matrix-multiply-accumulate (MMA) units introduced in NVIDIA Volta (2017). They compute D = A × B + C on 16×16 or 8×16 matrices in a single operation, far faster than using CUDA cores for the same computation:

H100 4th-gen Tensor Core operation (per cycle per unit): Input: A ∈ ℝ^{16×8} (BF16), B ∈ ℝ^{8×16} (BF16) Output: D ∈ ℝ^{16×16} (FP32) FLOPs: 16×16×8 × 2 (mul+add) = 4,096 FLOPs per MMA per cycle Total Tensor Core throughput (BF16 → FP32, H100): 528 units × 4,096 FLOPs × 1.8 GHz boost clock ≈ 3.9 PFLOPS (Measured/published: 1,979 TFLOPS — reflects actual achievable with memory limitations) FP8 Tensor Core throughput (H100): 3,958 TFLOPS → 2× BF16 INT8 Tensor Core throughput (H100): 3,958 TOPS

Read peak FLOPS with suspicion Vendors increasingly quote peak throughput at the lowest supported precision, and sometimes for a whole multi-die package or an entire rack rather than a single chip. A "20 PFLOPS" claim may be FP4 with structured sparsity assumed, across two dies. Comparing generations honestly means fixing the precision, fixing the unit (die, package, or rack), and ignoring sparsity multipliers. The number that actually predicts training throughput for most workloads is BF16 or FP8 dense, and the number that predicts inference throughput is usually memory bandwidth, not FLOPS at all.
H100 vs H200: same chip, different memory The H200 uses the same Hopper GPU die as the H100, but with HBM3e (next-gen HBM) instead of HBM3. Memory capacity jumps from 80 GB to 141 GB (75% increase), and bandwidth from 3.35 TB/s to 4.8 TB/s (43% increase). This is primarily a win for inference: larger KV caches, larger batch sizes, more memory-bandwidth-bound throughput. Training FLOPs are unchanged — the same 1,979 TFLOPS BF16.

Blackwell Architecture (B200)

The B200 (2025) introduces a dual-die design — two Blackwell GPU dies connected via NVLink with 1.8 TB/s die-to-die bandwidth. Together they function as a single logical GPU:

B200 SXM: - 2× Blackwell dies per package (connected via 10 TBs NVLink-C2C) - 192 GB HBM3e across 8 stacks (24 GB per stack) - Memory bandwidth: 8,000 GB/s (2.4× H100) - FP4 Tensor Core: 20 PFLOPS peak - FP8 Tensor Core: 9 PFLOPS peak (vs 3.96 for H100) - GB200 NVL72 rack: 36 Grace CPU + 72 B200 GPU modules → 1,440 TB/s NVLink fabric within a rack → 720 GB/s per B200 of NVLink bandwidth

The Rack Became the Unit of Compute

The most consequential change in the Blackwell generation is not the die — it is that NVIDIA stopped selling servers and started selling racks. A GB200 NVL72 rack presents 72 GPUs joined by a single NVLink domain, so that from software's point of view the rack behaves like one very large accelerator with a shared, coherent pool of memory. This matters enormously for two workloads: training very large mixture-of-experts models, where expert weights must be sharded across many devices, and serving long-context reasoning models, where the KV cache exceeds any single GPU's memory.

It also changes the data centre. A 72-GPU rack draws on the order of 120 kW, which is roughly ten times the density of a conventional air-cooled rack and beyond what air can remove. Direct-to-chip liquid cooling stops being an optimisation and becomes a requirement, and power distribution moves toward higher-voltage DC architectures. See Training Data Centers for what that does to the building.

The Published Roadmap

  • 2020–2022Ampere → Hopper

    A100 to H100. Tensor core generations three and four; FP8 arrives with Hopper; the transformer era's workhorses.

  • 2024–2025Blackwell and Blackwell Ultra

    Dual-die packages, FP4 tensor cores, HBM3e, and the shift to rack-scale NVLink domains. Blackwell Ultra (GB300) adds memory capacity and power headroom aimed squarely at long-context reasoning inference.

  • 2026Rubin

    Announced to pair a new GPU with a new Arm CPU (Vera), HBM4, and roughly doubled NVLink bandwidth. HBM4 is the headline change: the interface widens to 2,048 bits per stack, which is the single biggest lever available for inference throughput.

  • 2027 and beyondRubin Ultra, then Feynman

    Named on public roadmaps with an annual cadence. Treat named future parts as statements of intent that shape customer purchasing decisions as much as they describe silicon — announcing a roadmap is itself a competitive act.

The annual cadence is a strategic weapon NVIDIA moved from a roughly two-year architecture cycle to an annual one. This is punishing for competitors — a rival that takes three years to ship a chip competitive with last year's part is permanently behind — and it is punishing for customers too, since it shortens the economically useful life of hardware they have just bought. That second effect is exactly the depreciation argument discussed on the Economics page. A faster roadmap is good for the industry's capability and awkward for its balance sheets.

Google TPUs: Custom AI ASICs

Google developed Tensor Processing Units (TPUs) internally starting in 2015, motivated by the explosive growth of TensorFlow inference compute. Unlike GPUs, TPUs are purpose-built for tensor operations with no pretence of general-purpose computing.

Why Google's vertical integration matters more than the specifications TPUs let Google train and serve its frontier models without paying an accelerator vendor's margin, and without competing for allocation in a supply-constrained market. That is a structural cost advantage no amount of per-chip benchmarking captures. It is also why every other hyperscaler has built its own silicon, and why NVIDIA's ~90% share of the merchant accelerator market understates how much AI compute it actually touches — a large and growing fraction of the world's AI compute now runs on chips that were never sold to anyone.

TPU Architecture vs GPU

GPU (H100)

Many parallel SIMT cores (16,896). Large SRAM L2 cache (50 MB). Flexible: handles diverse computation graphs, branchy code, variable-length operations. Rich software ecosystem (CUDA, 3,000+ libraries). Requires skilled kernel programmers for peak performance. Memory in external HBM stacks.

TPU (v5p)

Systolic array matrix engine — data flows through an array of multiply-accumulate units like water through a grid. Extremely efficient for fixed GEMM shapes. Simpler control logic → more die area for MACs. Inter-chip interconnect (ICI) is on-chip, not via PCIe. Less flexible: dynamic shapes and control flow are expensive. Optimised for XLA (JAX/TensorFlow), not CUDA.

TPU Systolic Array

A systolic array computes C = A × B by streaming A and B through an array of PEs: Example: 128×128 systolic array Row i of A flows rightward through row i of PEs. Column j of B flows downward through column j of PEs. PE(i,j) accumulates: C(i,j) += A(i,k) × B(k,j) as data pulses through. After 128 cycles: entire 128×128 matrix product is computed. No random memory access needed — data is delivered rhythmically. This regularity makes the TPU extremely area and power efficient for GEMM.

Memory Hierarchy

Every GPU operation navigates a memory hierarchy. Bandwidth and capacity trade off at every level:

High Bandwidth Memory (HBM)

Conventional GDDR memory (used in gaming GPUs) achieves 500–700 GB/s by using many narrow channels at high frequency. HBM takes a different approach: stack multiple DRAM die vertically and connect them through-silicon vias (TSVs):

HBM3 structure (one stack): - 12 DRAM die stacked vertically (12-Hi) - Connected by TSVs (through-silicon vias): ~10,000 vias per stack - 1,024-bit wide bus (LPDDR5: 64-bit; DDR5: 64-bit; HBM3: 1024-bit!) - Per-stack bandwidth: 819 GB/s at 6.4 Gbps/pin - H100 has 6 HBM3 stacks: 6 × 819 = 4,914 GB/s raw → ~3,350 GB/s actual The HBM stack sits adjacent to the GPU die on a silicon interposer (CoWoS packaging). The short, wide bus (TSV) is the key: it's like replacing one narrow pipe with 1,024 parallel pipes. Power per bit transferred: ~3× lower than GDDR (short distance, lower voltage). HBM evolution: HBM1 (2015): 128 GB/s per stack HBM2 (2016): 256 GB/s HBM2e (2019): 460 GB/s (A100 uses 6 stacks = 2,000 GB/s) HBM3 (2022): 819 GB/s (H100) HBM3e (2024): ~1,200 GB/s per stack (H200/B200 use 8 stacks) HBM4 (2026): ~2,000 GB/s per stack — the interface doubles from 1,024 to 2,048 bits, the first width change since HBM1 Why HBM4's width change is the important one: Bandwidth = bus width × transfer rate. Vendors have been raising the transfer rate for a decade, and it is running into signal-integrity and power limits. Doubling the width sidesteps that — at the cost of far more through-silicon vias, a harder interposer, and tighter packaging tolerances, which is why advanced packaging capacity, not wafer capacity, has been the binding constraint on accelerator supply. See the Foundry page. HBM is also a genuine oligopoly: SK Hynix, Micron and Samsung. Qualification for a given accelerator takes years, so supply agreements are signed generations in advance and pricing power sits with the memory makers to an extent unusual in semiconductors.

The CUDA Software Stack

CUDA (Compute Unified Device Architecture), introduced by NVIDIA in 2006, is the programming model and runtime that makes GPUs programmable for general compute. It is the primary reason NVIDIA dominates AI — AMD's ROCm and Intel's oneAPI are years behind in ecosystem maturity.

CUDA Programming Model

CUDA thread hierarchy: Thread: single execution unit, has private registers Warp: 32 threads, executed in lockstep (SIMT) Block: up to 1,024 threads, share L1/SRAM, synchronise cheaply Grid: many blocks, distributed across all SMs automatically A CUDA kernel (GPU function) is written once and launched on a grid. The CUDA runtime schedules blocks to available SMs. Example: Matrix multiplication kernel for C = A × B Launch grid: (M/32, N/32) blocks Each block: 32×32 threads computing a 32×32 tile of C Shared memory: load A-tile and B-tile into SRAM, reuse many times → Reduces HBM accesses by factor of 32 (tile size) → This tiling is why GPU matrix multiply can approach theoretical peak throughput

Occupancy and Efficiency

Occupancy = active warps / maximum resident warps Higher occupancy hides latency: while one warp waits for memory, the SM switches to another warp instantly (zero context-switch cost). Occupancy limited by: - Register usage: 256K registers/SM, if kernel uses 128 registers/thread: max threads = 256K/128 = 2,048 → full occupancy - Shared memory: 228KB/SM, if kernel uses 50KB/block: max blocks = 228/50 = 4 blocks × 1,024 threads = 4,096 threads → 2× oversubscribed, fine - Instruction throughput: if compute-bound, occupancy above 50% gives diminishing returns

The Competition, and Why the Moat Held So Long

In plain terms

NVIDIA's real advantage was never only the chips. It was that twenty years of software — libraries, compilers, tuned kernels, tutorials, and the accumulated habits of every machine-learning engineer alive — assumed NVIDIA hardware. A competitor has to beat all of that, not just the silicon. What has changed recently is that most people no longer write kernels at all; they call PyTorch or a serving engine, and those now have working non-NVIDIA backends.

AMD has closed much of the hardware gap. The MI300X line led on memory capacity and bandwidth — genuinely advantageous for inference, where memory is usually the constraint — and successive generations have narrowed the compute gap while ROCm has matured from "technically supported" to "used in production by serious customers." Very large accelerator commitments from major AI developers have followed. The remaining disadvantage is concentrated in training at the largest scales, where NVIDIA's networking, collective-communication libraries and rack-scale integration remain ahead, and where the cost of a stalled 20,000-GPU run makes engineering teams conservative.

Custom silicon is the larger competitive story. Every hyperscaler now designs its own accelerators — Google's TPUs, Amazon's Trainium and Inferentia, Microsoft's Maia, Meta's MTIA — typically with Broadcom or Marvell as design partner. These chips do not need to beat NVIDIA on any benchmark. They need only to be good enough at the operator's own dominant workload to be cheaper in total cost of ownership, and they answer to an internal customer who will do the porting work.

Specialist inference hardware attacks from a third direction. Wafer-scale processors and architectures that keep model weights entirely in on-chip SRAM sidestep HBM bandwidth altogether, delivering token generation speeds that HBM-based designs cannot match. They are constrained by the model sizes their on-chip memory can hold, so they occupy a real but bounded niche — a niche that matters more as reasoning models make output tokens the dominant cost.

Where the moat is now thinnest Training at frontier scale still strongly favours NVIDIA: the networking, the collectives, the rack-scale NVLink domains and the operational maturity compound. Inference is a different market. Serving is dominated by a handful of engines (vLLM, SGLang, TensorRT-LLM) that abstract the hardware, the workload is memory-bandwidth-bound rather than kernel-bound, and buyers are acutely price-sensitive because inference is a recurring cost rather than a capital one. If NVIDIA's share erodes, it will erode there first — and inference is where the volume is heading.

Ethernet is eating the AI network InfiniBand won the first round of AI networking on latency and its mature RDMA implementation. Ethernet is winning the second, for unglamorous reasons: more suppliers, lower cost, existing operational expertise, and a specification effort (the Ultra Ethernet Consortium) explicitly targeting the congestion control and lossless behaviour that AI collectives require. At the very largest scales the two now coexist — a proprietary high-bandwidth domain inside the rack, Ethernet between racks. The next frontier is optics: as clusters grow, the power and reach limits of copper push toward co-packaged optical interfaces, where the fibre terminates on the switch package itself.

Key takeaways

  • GPUs win because neural network training is almost entirely dense matrix multiplication, which is embarrassingly parallel and needs no branch prediction or out-of-order execution.
  • Tensor cores, not CUDA cores, do the real work: they perform small matrix multiply-accumulate operations as single instructions, at an order of magnitude higher throughput.
  • Peak FLOPS figures are quoted at ever-lower precisions and ever-larger units. Fix the precision and the unit before comparing anything.
  • For inference, memory bandwidth predicts performance better than FLOPS — which is why HBM generations, and HBM4's doubled bus width, matter so much.
  • The unit of compute is becoming the rack, not the chip, which forces liquid cooling and new power architectures into the data centre.
  • NVIDIA's moat is strongest in frontier training and weakest in inference, where serving engines abstract the hardware and buyers are price-sensitive.
