Inference

AI Inference: Putting Models to Work

Inference is the production workload: executing a trained model billions of times per day with tight latency requirements, at a fraction of the cost of training. The engineering challenges are fundamentally different from — and in many ways harder than — training.

What Inference Is

Training updates weights; inference uses them. Given fixed model parameters θ, inference computes fθ(x) for a new input x — a pure forward pass with no gradient computation. But for autoregressive language models, inference has a distinctive structure that creates unique engineering challenges.

Autoregressive Generation

A language model does not generate the full response in one shot. It generates one token at a time, each token conditioned on all previous tokens — including those it just generated:

Given prompt x₁, x₂, …, xₙ: Step 1: P(t_{n+1} | x₁…xₙ) → sample token t_{n+1} Step 2: P(t_{n+2} | x₁…xₙ, t_{n+1}) → sample token t_{n+2} Step 3: P(t_{n+3} | x₁…xₙ, t_{n+1}, t_{n+2}) → ... Each step requires a full forward pass through all L transformer layers. A 500-token response = 500 sequential forward passes.

This sequential dependency — each token depends on the previous — is the fundamental bottleneck of LLM inference. It cannot be parallelised in the generation direction, unlike training where all positions in a sequence are processed simultaneously (the transformer processes all positions in a forward pass; during training we just mask future positions).

Prefill vs Decode Inference has two distinct phases. The prefill phase processes the entire input prompt in parallel (all tokens simultaneously, like training). It is compute-bound and typically takes 10–100 ms. The decode phase generates one token per step, sequentially. Each decode step processes a single token attending to the full context — it is memory-bandwidth-bound, not compute-bound, because GPU compute sits idle while waiting for model weights to be streamed from HBM.

KV Cache

In the transformer's self-attention mechanism, every token attends to every previous token. Computing attention naively at every decode step would require recomputing the Key (K) and Value (V) vectors for all past tokens from scratch — O(n²) work per sequence of length n.

The KV cache stores the K and V tensors for all past tokens in GPU memory, so each decode step only computes K, V for the single new token and reads the cached vectors for context:

At decode step t, for attention head h: Recomputed: Q_t = x_t W_Q [1 query vector] Retrieved: K_{1:t} from KV cache [t cached key vectors] V_{1:t} from KV cache [t cached value vectors] Attention: a_t = softmax(Q_t K_{1:t}ᵀ / √d_k) · V_{1:t} KV cache size per token = 2 × n_layers × n_heads × d_head × sizeof(dtype) For Llama-3 70B (80 layers, 64 heads, d_head=128, BF16): = 2 × 80 × 64 × 128 × 2 bytes = 2.62 MB per token For 4,096 context tokens: 2.62 MB × 4096 ≈ 10.7 GB of KV cache

The KV cache trades memory for compute — a fundamental tradeoff. Longer context windows require proportionally more KV cache memory, which is why serving very long contexts (128K+ tokens) at scale is expensive: the KV cache alone can dominate GPU memory.

PagedAttention

Standard KV caching allocates a contiguous block of memory per request at maximum context length — leading to severe internal fragmentation when requests have variable lengths. The vLLM framework introduced PagedAttention (2023), which manages KV cache in non-contiguous "pages" (blocks of ~16 tokens), analogous to virtual memory paging in an OS. Requests share physical pages, and pages are allocated on demand. This improves GPU memory utilisation from ~30% to ~90% on typical workloads, increasing throughput 2–4×.

Sampling Strategies

The model outputs a distribution over the vocabulary — a vector of logits zᵥ for each of V possible next tokens. The sampler converts this into a single token choice:

Greedy Decoding

token = argmax_v softmax(z_v) [always picks the most probable token]

Fast and deterministic. Poor for open-ended generation — tends toward repetitive, bland text.

Temperature Sampling

P(token = v) = softmax(z_v / T)_v = e^{z_v/T} / Σ_w e^{z_w/T} T → 0 : greedy decoding (argmax) T = 1 : sample from model's distribution as trained T > 1 : flatten distribution, more random/creative T → ∞ : uniform distribution over all tokens

Top-k and Top-p (Nucleus) Sampling

Top-k: restrict sampling to the k highest-probability tokens, renormalise, sample. Typical k = 40–100. Top-p: sort tokens by probability (descending). Include tokens until cumulative probability ≥ p, renormalise, sample. Typical p = 0.9–0.95. Adaptive: automatically includes more tokens when distribution is flat (uncertainty high) and fewer when it is peaked (clear best option).

Most production systems use top-p with temperature. A temperature of 0.7 and p=0.9 is a common default — creative enough to avoid repetition, constrained enough to avoid incoherence.

Quantisation

Model weights stored in FP16 or BF16 require 2 bytes per parameter. Quantisation compresses weights to lower precision, reducing both memory footprint and — critically — memory bandwidth consumption during decode (which is the primary bottleneck).

Quantisation maps floating-point values to integers: INT8 (W8A8): 8-bit weights AND 8-bit activations x_q = round(x / scale + zero_point) x_deq = (x_q − zero_point) × scale Memory: 1 byte/parameter (2× over BF16) Throughput: 2× increase on INT8 tensor cores INT4 (W4A16): 4-bit weights, 16-bit activations (dequantise at matmul) Memory: 0.5 bytes/parameter (4× over BF16) A 70B model: 70B × 0.5 = 35 GB — fits on a single H100 80GB! GPTQ / AWQ: group-wise quantisation, calibrated on small dataset. Minimises quantisation error by finding optimal scale per group of 128 weights.
Quality vs compression tradeoff INT8 quantisation typically degrades model quality by 0.1–0.5% on benchmarks — often acceptable. INT4 can degrade by 1–3% on complex tasks. Careful calibration (AWQ, GPTQ, SmoothQuant) narrows this gap significantly. FP8 (8-bit floating point, E4M3 format) is now natively supported on H100/H200 GPUs and offers INT8 compression with FP16-comparable quality because the exponent representation is retained.

Activation-Weight vs Weight-Only Quantisation

During decode, the bottleneck is reading weight matrices from HBM into the GPU's SMs — weight-only INT4 (W4A16) maximally reduces this read, then dequantises to FP16 for the actual matrix multiplication. During prefill, compute is the bottleneck, so W8A8 (both weights and activations in INT8) improves compute throughput on tensor cores.

Speculative Decoding

Speculative decoding (Leviathan et al., 2022) uses a small, fast draft model to generate K candidate tokens, which the large target model then verifies in a single batched forward pass:

Algorithm: 1. Draft model (e.g. 7B) autoregressively generates K=4 tokens: d₁, d₂, d₃, d₄ 2. Target model (e.g. 70B) processes the full sequence [prompt, d₁, d₂, d₃, d₄] in ONE forward pass (parallel, like prefill). Produces: P_target(·|prompt), P_target(·|prompt,d₁), …, P_target(·|…,d₃) 3. Accept/reject each draft token using: Accept dᵢ with probability min(1, P_target(dᵢ|ctx) / P_draft(dᵢ|ctx)) If rejected: sample from corrected distribution and stop. 4. On average, if draft acceptance rate α ≈ 0.7, we accept 0.7×4 = 2.8 tokens per step. Total time ≈ 1 large model forward pass ≈ time of 4 draft steps. Net speedup ≈ 2.8× (at constant hardware utilisation).

The key insight: the target model forward pass over K+1 tokens costs the same as 1-token decode on modern GPUs (memory bandwidth bound, not compute bound). Verifying K tokens at once is "free" compute if the GPU otherwise idles waiting for memory.

Inference Metrics and Service-Level Objectives

TTFT
Time to First Token — latency from request submission to first token appearing. Includes queueing + prefill. Target: <200 ms for chat.
ITL
Inter-Token Latency — time between consecutive generated tokens. Target: <30 ms (33 tokens/sec) to feel real-time to users.
Throughput
Tokens/second across all concurrent users. Often measured as output tokens per second per GPU.
MBU
Memory Bandwidth Utilisation — decode is memory-bound; H100 peak is 3.35 TB/s. Good inference engines achieve 60–80% MBU.

The Batching Tradeoff

Processing multiple requests simultaneously (batching) increases throughput — the GPU is better utilised. But it adds latency for individual requests (requests wait in queue, longer decodes, larger KV caches). The optimal batch size maximises throughput while staying within latency SLOs. Continuous batching (Orca, 2022) dynamically adds new requests to a running batch as existing ones complete — rather than waiting for all requests in a batch to finish before accepting new ones. This dramatically improves GPU utilisation for variable-length workloads.

Compute vs Memory Bandwidth: The Core Tradeoff

Whether inference is compute-bound or memory-bound determines which optimisations matter. The key ratio is the arithmetic intensity — FLOPs per byte of memory access:

Arithmetic intensity = FLOPs / Bytes accessed For matrix-vector multiplication (single decode step, batch size=1): - Weight matrix W ∈ ℝ^{d×d}: d² parameters = d² × 2 bytes (BF16) - FLOP count: 2d² (d multiplications + d additions per output element) - Intensity = 2d² / (2d²) = 1 FLOP/byte H100 peak: - Compute: 1,979 TFLOPS (BF16) - Memory BW: 3,350 GB/s = 3,350 × 10⁹ bytes/s - Machine balance: 1,979 × 10¹² / 3,350 × 10⁹ ≈ 591 FLOPs/byte For single decode step: intensity (1) << machine balance (591) → GPU is >99% idle on compute; 100% bound by memory bandwidth

This is why throughput scales linearly with memory bandwidth, not TFLOPS, during single-request decode. Batching raises arithmetic intensity: with batch size B, each weight matrix element serves B queries — intensity ≈ B FLOPs/byte. At B ≈ 591, the workload becomes compute-bound. Production inference systems tune batch size to hit this crossover point.
